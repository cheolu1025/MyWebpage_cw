2026년 2학기 클라우드컴퓨팅 수업의 기말 프로젝트로 진행 중인 Pick & Keep의 기획·설계 기록입니다.
아직 구현을 시작하기 전 단계로, 지금까지 정한 내용과 직접 확인한 것, 앞으로의 계획을 정리했습니다.

<!--more-->

## 개요

- 수업: 2026년 2학기 클라우드컴퓨팅 (기말시험을 대체하는 프로젝트)
- 형태: 2인 팀, 팀원과 함께 기획과 설계를 진행
- 현재 상태: 진행 중 (주제·기능 확정, 시스템 설계, 제안 발표 완료 / 구현 시작 전)
- 실습 환경: AWS Academy Learner Lab
- 사용 예정 기술: Python, Flask, boto3, Pillow, SQLite, AWS EC2·S3·Rekognition·IAM
- 제안 발표 자료: [Pick & Keep 제안 발표 (PDF, 약 0.4MB)](pick-and-keep-proposal-slides.pdf)

## 문제의식

기존 클라우드 사진 서비스는 사진을 한꺼번에 백업하기 때문에, 필요 없는 스크린샷이나 흔들린 사진까지 저장공간을 차지합니다.
휴대폰은 용량이 정해져 있어 늘리려면 기기를 바꿔야 하고, 클라우드는 용량에 제한이 없는 대신 쓴 만큼 비용이 계속 쌓입니다.
그래서 사진을 먼저 분류하고 필요한 사진만 골라 백업하면, 휴대폰과 클라우드 양쪽의 공간과 비용을 함께 줄일 수 있다는 점에 착안했습니다.

## 핵심 기능

- 평생 보관함: 가족, 여행, 졸업 사진처럼 오래 남길 사진을 보관합니다. 처음에는 자주 볼 가능성이 높아 일반 등급에 두고, 90일이 지나면 저렴한 장기 보관 등급으로 자동 전환합니다.
- 보류함: 맛집 메뉴판이나 쇼핑 캡처처럼 나중에 쓸 수도 있는 사진을 임시로 보관합니다. 60일 동안 한 번도 열어 보지 않으면 삭제, 연장, 평생 보관함으로 이동 중 하나를 사용자에게 묻습니다.
- 확보 용량 표시: 보관함에 올린 사진과 지워도 되는 사진 목록을 보여 주고, 기기에서 정리하면 확보되는 용량을 함께 보여 줍니다.

여기서 가장 중요하게 정한 원칙은 사용자 중심 설계입니다.
AI는 사진을 강아지, 음식, 풍경, 스크린샷 같은 종류별 묶음으로 보여 주기만 하고, 어디에 보관할지는 사용자가 묶음 단위로 최종 결정합니다.

## 시스템 설계

모바일 앱 개발 경험이 없는 팀 상황과 폰·PC 모두에서 쓸 수 있다는 점을 고려해, 앱 설치 없이 브라우저로 쓰는 웹 서비스로 설계했습니다.

1. 사용자가 브라우저에서 사진을 올리면 EC2의 Flask 웹 서버가 받습니다.
2. 스크린샷은 파일 정보와 형식 같은 규칙으로 먼저 걸러 내고, 나머지 사진만 Amazon Rekognition으로 분석해 종류별로 묶습니다.
3. 사용자가 고른 사진만 S3 버킷의 평생 보관함(keep/)과 보류함(hold/) 폴더에 저장합니다.
4. 버킷은 외부에 공개하지 않고, 사진을 볼 때만 잠깐 쓸 수 있는 임시 링크(Presigned URL)를 발급합니다.

EC2는 액세스 키 대신 IAM 역할로 S3와 Rekognition에 접근하고, 보안 그룹으로 필요한 포트만 열어 둡니다.
사진 정보와 마지막으로 열어 본 시각은 SQLite에 기록해 보류함 60일 판단에 사용합니다.

## 설계하면서 내린 결정

- 처음부터 장기 보관 등급에 넣지 않는 이유: 장기 보관 등급은 보관료는 싸지만 꺼낼 때 비용과 최소 보관 기간이 있어, 업로드 직후 자주 보는 사진에는 일반 등급이 더 유리합니다. 보관 등급은 사진의 중요도가 아니라 접근 빈도로 정한다는 기준을 세웠습니다.
- 보류함을 일반 등급으로 두는 이유: 60일 안에 지워질 수 있는 사진에 최소 보관 기간이 있는 등급을 쓰면 오히려 비용이 늘기 때문입니다.
- S3의 자동 삭제 규칙을 쓰지 않는 이유: 자동 삭제는 업로드 날짜를 기준으로 사용자에게 묻지 않고 지웁니다. 우리는 실제로 열어 본 기록을 기준으로 삼고, 지우기 전에 반드시 사용자에게 확인하도록 직접 구현하기로 했습니다.
- 스크린샷을 AI로 분석하지 않는 이유: 규칙만으로 판별할 수 있으므로, 분석 요청 비용과 처리 시간을 아낄 수 있습니다.

## 지금까지 확인한 것

- Learner Lab 환경에서 Rekognition의 라벨 분석(DetectLabels)이 실제로 동작하는 것을 확인했습니다.
- S3에 사진을 장기 보관 등급(Glacier Instant Retrieval)으로 업로드할 수 있는 것을 확인했습니다.
- 테스트 중 발견한 제약도 설계에 반영했습니다.
  - Learner Lab 세션이 4시간 뒤 멈추고 재시작하면 서버 주소가 바뀌므로, 서버 생성 시 설치를 자동화하고 시연 전 주소를 확인하기로 했습니다.
  - 한글 파일명은 S3 주소에서 깨져 보여, 저장 이름은 날짜와 영문·숫자 조합으로 만들고 원래 이름은 데이터베이스에 따로 저장하기로 했습니다.
  - 장기 보관 등급은 최소 보관 요금이 있어, 반복 테스트는 일반 등급으로 하기로 했습니다.
  - 세션이 멈추면 정기 실행 작업이 불안정해, 보류함 검사는 사용자가 접속할 때 실행하도록 정했습니다.

## 다음 계획

앞으로 약 6주에 걸쳐 다음 순서로 구현할 계획입니다.

1. EC2 웹 서버 구축, 사진 업로드, 스크린샷 판별과 Rekognition 분류 연동
2. 종류별 묶음과 보관 위치 선택 화면, 평생 보관함·보류함 저장, 보관함 조회, 확보 용량 표시
3. 장기 보관 등급 전환 규칙 설정, 보류함 60일 검사와 알림, 배포 자동화, 통합 테스트와 최종 발표

현재 구조는 서버 한 대와 서버 내부 데이터베이스에 의존해, 서버가 멈추면 서비스 전체가 멈추는 한계가 있습니다.
수업 프로젝트 범위에서는 이 구조로 기능 구현에 집중하고, 이후에는 여러 가용 영역과 별도 데이터베이스로 확장하는 방향을 검토할 생각입니다.
